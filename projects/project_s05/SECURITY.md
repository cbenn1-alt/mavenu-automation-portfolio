# S05 — Security Notes

> **⚠ EDUCATIONAL DEMO ONLY — NOT PRODUCTION CRYPTOGRAPHY.**
> README forbids production use without expert review.

## Threat model (what this project defends against — and what it doesn't)

**In scope (demonstrated):** tampered ciphertext (encrypt-then-MAC,
verify-before-decrypt); weak/hardcoded keys (policy rejects them);
timing oracles on comparisons (`hmac.compare_digest` everywhere);
nonce reuse (256-bit random nonces; replays rejected); ECB-pattern
equality leaks (demonstrated as the DON'T); key-compromise blast radius
(rotation, destruction, re-encryption procedure).

**Out of scope (stated, not tested):** side-channel attacks on hardware
(power, EM, cache timing) — conceptual coverage only, no hardware testing;
the educational stream cipher has no security argument and no review — it
must never protect real data; the web API is a demo surface with no
authentication, rate limiting, or transport security — it is not a service.

## Timing side-channels

All secret-dependent comparisons use `hmac.compare_digest`:
`hmac_verify()`, `decrypt()` (tag check), `mac_verify()`, and
`verify_password()`. Plain `==` is never used on tags, MACs, or password
hashes anywhere in the module. Rationale documented in PITFALLS P-TIMING:
a byte-at-a-time timing oracle is the classic failure this prevents.

## Randomness

All key material, nonces, and salts come from `secrets` (OS CSPRNG).
`random` is never used for cryptographic material — there is no
`import random` in `crypto_demo.py`. Test determinism (fixed nonces/salts)
is opt-in per call and documented as test-only.

## Demo keys are test-only

Every key generated by the module, the web demo, and the API is synthetic
and labeled test-only (banner in API responses, `note` column in the
registry, docstrings). The registry stores hex-encoded demo keys — fine
for teaching, unacceptable for real secrets (real tiers: HSM/KMS >
secret manager > encrypted-at-rest; never source control).

## Input validation at boundaries

- `sha256()`/`hmac_*()` reject non-bytes (`TypeError`).
- `validate_key()` rejects short, blocklisted, all-zero, repeated-byte,
  and non-bytes keys (`WeakKeyError`) — called by every entry point.
- `decrypt()` rejects malformed envelopes (`CryptoError`), wrong-length
  tags, replays (`NonceReusedError`), and bad tags (`TamperDetectedError`).
- `verify_password()` returns `False` (never raises) on malformed stored
  strings — no oracle on format errors.
- Password API floor: the web endpoint refuses work factors below 10,000
  (NIST SP 800-63B floor); the module floor is 1 so tests stay fast —
  documented in ARCHITECTURE.md.
- Web layer: JSON schema checks return 422; crypto failures return 422
  with `auth_failed`/`key_error` codes, never stack traces with key material.
- SQL: parameterized queries only (inherited project convention).

## What "fails closed" means here

Every misuse path raises an exception or returns an explicit `False`:
tampered → raise; replayed → raise; weak key → raise; destroyed key →
raise; unknown version → raise; malformed input → raise/False. No path
returns plausible-looking wrong output. Verified by the misuse suite (M3).

## Residual risks (honest)

1. The educational cipher is unreviewed — the banner is the mitigation,
   plus the pointer to audited libraries. If someone strips the banner,
   the code cannot stop them; the docs forbid it in plain language.
2. The replay cache is session-scoped; a restarted process forgets replays.
   Documented as demo-grade.
3. PBKDF2 (not memory-hard like Argon2/scrypt) is the KDF because it is
   stdlib; the work-factor guidance and per-password salts are the honest
   compensations, documented in §4 of the module.
4. No constant-time guarantee beyond `compare_digest` — the Python-level
   keystream XOR is not hardened against microarchitectural side channels.
   Stated, not tested on hardware.
